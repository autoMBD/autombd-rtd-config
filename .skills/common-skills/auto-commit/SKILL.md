# Auto Commit

## Core Principle

Commit proactively after every meaningful unit of work. Do NOT wait for the user to request a commit. Do NOT batch unrelated changes into one commit. Each commit must represent a single, logical, independently-reviewable change.

## When to Commit — Trigger Checklist

Commit when any of these completes:

- A new function, module, or file is finished and compiles
- A bug is fixed and the fix is verified
- A refactor step finishes with no behavioral change
- A test is added or updated for a specific feature
- Documentation is updated for a completed feature (not in-progress drafts)
- One step of a multi-step task plan is done
- A review comment is addressed and the change stands alone
- Configuration or build changes that support a completed feature

Do NOT commit:

- Mid-edit, broken, or half-typed code
- Work-in-progress drafts of documentation
- Experimentation scratch files
- Work that hasn't been reviewed or sanity-checked

## Granularity

Before staging, ask: "Does this set of changes tell one coherent story?" If the answer is no, split into multiple commits.

- **One feature = one commit** (unless it is large enough to warrant steps)
- **One bugfix = one commit**
- **One refactor = one commit** (rename, extract function, etc.)
- **Style/whitespace-only changes** get their own commit, isolated from logic changes

## Branch Discipline

- Commit to the **current branch only**
- **NEVER** switch branches, create branches, or checkout another branch unless the user explicitly asks
- If unsure which branch you're on: run `git branch --show-current` first

## File Selection — What to Stage

```bash
# Preferred: stage specific files
git add src/core/mc33937/mc33937_cli.c include/core/mc33937/mc33937_cli.h
```

- Use `git add <specific files>` — never `git add -A` or `git add .`
- Verify staged files with `git status` and `git diff --cached` before committing
- Respect `.gitignore` absolutely — if a file is ignored, never force-add it without asking

### NEVER Stage (zero-tolerance)

| Category | Examples |
|---|---|
| Build artifacts | `*.o`, `*.obj`, `*.elf`, `*.bin`, `*.hex`, `*.map`, `*.a`, `*.lib`, `build/`, `out/` |
| IDE files | `.vscode/`, `.idea/`, `*.swp`, `*.swo`, `*~`, `*.launch` |
| Temp/cache | `*.tmp`, `*.log`, `*.stackdump`, `*.bak`, `.DS_Store` |
| Generated code | `Debug/`, `Release/`, `CMakeFiles/`, `generate/`, `RTD/` |
| Secrets | `.env`, `credentials.*`, any file containing tokens or keys |
| Agent runtime | `.claude/*`, `.agents/*`, `.codex/*` (skill symlinks generated by `sync_agent_skills.py`) |

If a file appears in `.gitignore`, do NOT stage it. If you think an exception is warranted, ask the user explicitly.

## Commit Message Format

```
<type>(<scope>): <imperative subject, lowercase, under 72 chars, no period>

<optional body — explain WHY, not what. Wrap at 72 chars.>
```

### Types

| Type | Use when |
|---|---|
| `feat` | New feature or capability |
| `fix` | Bug fix |
| `refactor` | Code restructuring, no behavior change |
| `docs` | Documentation only (README, comments, guides) |
| `test` | Adding or updating tests |
| `chore` | Build, tooling, CI, dependencies, maintenance |
| `style` | Formatting, whitespace, semicolons — no code logic change |

### Scope

Use the component or module name: `cli`, `mc33937`, `spi`, `gpio`, `hal`, `build`, `debug`, `trace`, `timer`, etc. Omit if the change spans many scopes.

### Examples

```
feat(cli): add MC33937 command module registration
```
```
fix(spi): correct CPHA bit position in master mode
```
```
refactor(trace): extract ring buffer to static inline helpers
```
```
chore(build): add S32K3 register-HAL CMake library target
```

### Rules

- Subject: imperative, present tense ("add" not "added" or "adds")
- Subject: lowercase first letter
- Subject: no trailing period
- Subject: under 72 characters
- Body: blank line after subject, then explain WHY the change matters and any non-obvious context
- Body: wrap at 72 characters

## Workflow

Execute commits sequentially — one commit at a time:

1. Run `git status` to see all modified/untracked files
2. Run `git diff` to review changes
3. Identify logical groups of changes — if more than one, plan multiple commits
4. For each group:
   a. `git add <specific-files>`
   b. Write and confirm the commit message
   c. `git commit -m "$(cat <<'EOF' ... EOF)"`
5. After all commits are done, run `git status` to verify a clean state
6. Report: branch, commit count, and one-line summary of each commit

## Safety Rules

- **Never skip hooks**: no `--no-verify`, no `--no-gpg-sign`, no bypassing
- **Never amend**: if a hook fails, fix the issue, re-stage, and create a NEW commit. Do NOT use `git commit --amend`
- **Never force**: no `--force`, no `git reset --hard`, no destructive operations
- **Never push**: only push if the user asks, and only to the current branch
- **Never empty commits**: if there's nothing to commit, say so and move on
- **No Co-authored-by trailer**: do not add `Co-Authored-By` lines to agent-initiated commits

## Pre-Commit Hook Failure

If a commit is rejected by a pre-commit hook:
1. Read the hook output to understand what failed
2. Fix the issue in the source files
3. Run `git add` on the fixed files
4. Create a **new** commit (do NOT amend the failed one)

## Post-Commit Report

After committing, report to the user:

```
[auto-commit] branch: main
  abc1234 feat(cli): add MC33937 command module registration
  def5678 fix(spi): correct CPHA bit position in master mode
```

Keep the report concise — one line per commit, no filler.
