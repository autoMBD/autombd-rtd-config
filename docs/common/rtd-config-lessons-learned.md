## How this log is used

- Owner: the **Reviewer** subagent. After an iteration passes the test gate, the
  Reviewer records what the iteration taught — especially anything that *passed
  the green gate but was still wrong or risky* (the gate cannot catch everything).
- Every lesson must end in a **durable guard**: a new test, a provider/asset rule,
  a domain-truth/`.xdm` sourcing requirement, a Reviewer checklist item, or a
  Worker convention. A lesson without a guard is not done.
- Keep entries short and factual: what happened → root cause → the guard that
  prevents recurrence. Newest first.

| LL-013 | The exit-0 vendor gate passed while the inserted `DioChannel LED_CTRL` was ABSENT from generated code: the fixture carries `quick_selection="DioDefault"` on `<config_set name="Dio">`, which makes ConfigTools emit the factory-default Dio configuration and silently ignore every spliced channel, so `DioConf_DioChannel_LED_CTRL` never appeared in `Dio_Cfg.h` even though the `.mex` was well-formed and validation returned exit 0 with zero SEVERE. Separately (caught in review, not by the gate), the mscr→`DioPortId`(//16)/`DioChannelId`(%16) derivation — the core domain rule, verified against vendor `example_Dio.mex` (gpio,29→port1/chan13; gpio,50→port3/chan2) — has no anti-hardcode test: every passing test uses only PTA5 (→0/5), and a Reviewer mutation to `dio_port_id=0; dio_channel_id=5` passed all 21 tests; and `dio.json` repeats LL-012 (loader `_load_dio_asset` is dead code, all values are Python literals, and `test_dio_json_asset_has_correct_schema` checks asset self-consistency, not code==asset). | The `quick_selection` clear (an `attrib.pop`) was issued before a later `replace_element_region`, whose reload re-parses the tree and re-snaps `src.attrib` from raw bytes that still contain `quick_selection="DioDefault"`; `_render_minimal` then sees `element.attrib == src.attrib` and strips nothing, so the clear was lost. The gate only asserted exit 0 / well-formedness, never that the edit reached GENERATED code, so a config the tool "wrote" but the compiler never saw still scored green. The id-derivation and asset-equality were asserted only in prose/fixture-trivial values, so a hardcode or code/asset drift was invisible. | (a) Clear `quick_selection` on the carrier AFTER all insertions/reloads — it must be the last mutation before `write()`, never before a subsequent `replace_element_region` (verified BaseNXP/MCL/Port already comply). (b) The Tester's pass gate must verify the edit appears in GENERATED code (a codegen macro / pin assignment), not just exit 0, for EVERY insertion case; exit 0 + zero SEVERE is necessary but not sufficient (extends LL-003/LL-009). (c) A deterministic proxy test asserts the carrier's `quick_selection` is removed from the WRITTEN bytes (Test 7b) — mandatory for every quick_selection-bearing `config_set` an insertion touches. (d) Carry the LL-011 next-id/derived-value proof to the module's OWN computed ids, not just borrowed Port ids: add a test where a second pin yields a different mscr-derived `DioChannelId`/`DioPortId` so a hardcode fails. (e) Re-affirm LL-012: a committed asset must be loaded at runtime or pinned by a code==asset test; delete dead loaders like `_load_dio_asset`. |
| LL-012 | The Port asset `assets/nxp/s32k3/port/portpin.json` mis-attributes its provenance and is never loaded at runtime, yet the gate stayed green because every written value happens to match the fixture. (a) The asset declares `PortPinInitialMode` `"default": "PORT_GPIO_MODE"` with `source_ref "Port.xdm:PortPin/PortPinInitialMode"`, but `PORT_GPIO_MODE` is **not** in that field's `Port.xdm` RANGE (`PORT_PIN_MODE_ADC/_CAN/_DIO/...`) and the xdm DEFAULT is `PORT_PIN_MODE_DIO`. The real source of `PORT_GPIO_MODE` is the Pins-tool fixture (`Uart_Example.mex` uses it 4x; `PORT_PIN_MODE_DIO` 0x), so the value is operationally correct but the `.xdm` citation is false. (b) `apply.py` hardcodes the entire PortPin field set/order/defaults, the `<pin>` TX/RX templates, `_PACKAGE_PIN_FIELD`, and the Name convention as Python literals; `portpin.json` is referenced only in docstrings/comments ("grounded in portpin.json") and is read by no runtime code. The two truths can drift with nothing to catch it. | Domain-truth cross-check stopped at "the field name exists in `Port.xdm`" and never verified the specific *value* against the field's RANGE/DEFAULT; the ECUC `PortPinInitialMode` enum (which excludes `PORT_GPIO_MODE`) differs from the ConfigTools Pins-tool GUI mode label, and the asset conflated the two sources under one `source_ref`. The asset was authored as a documentation artifact in parallel with hand-written code literals, with no loader and no test asserting code==asset, so "grounded in portpin.json" is unenforced prose. | (a) Asset provenance must cite the *actual* source per value: a value that comes from the fixture/Pins-tool (e.g. `PortPinInitialMode=PORT_GPIO_MODE`) is labeled as fixture-derived, and any `source_ref "<Module>.xdm:..."` must name a value that is in that field's `.xdm` RANGE (or is the `.xdm` DEFAULT). Reviewer cross-checks the *value*, not just the field name, against RANGE/DEFAULT. (b) A committed asset that claims to be a template must be the runtime source of truth or be removed: either `apply_port_set` loads `portpin.json` for the field set/templates/package map, or a test pins the code literals against the asset so divergence fails the gate. A documentation-only "grounded in X" asset with no loader and no equality test is prohibited. (c) Recurrence of LL-011 in Port (dynamic `PortPinId=max+1`/struct-index are correct in code — Reviewer perturbed fixture ids 1-4→11-14 and got 15/16 — but no `test_port_apply.py` case perturbs the fixture, so a hardcoded 5/6 would pass all 18 tests): carry the LL-011 next-id-proof guard into **every** insertion module, not just MCL. |
| LL-011 | The next-available id computation for FlexIO logic channels (`apply_mcl_set`: new struct index, `FlexioMclChannelId`, `FlexioMclPinId`) is genuinely dynamic in the code — it scans existing entries and picks max+1 — but every committed test in `test_mcl_apply.py` runs only on the unmodified fixture (2 entries, so the answer is always index 2 / CHANNEL_2 / PIN_2). A regressed implementation that hardcoded index=2 / CHANNEL_2 / PIN_2 would pass all 10 tests, including idempotency (which short-circuits on the Name match before any id is computed). The vendor gate also stayed green because it validates a single insertion on that same fixture. | The "computed, not hardcoded" requirement was asserted only in prose (the module docstring and the asset `next_id_algorithm` field), never pinned by a test that changes the existing-entry set, so the property is unguarded against a future refactor. The new helpers (`_extract_channel_index` / `_extract_pin_index` malformed-to-None path, `_build_flexio_channel_struct_bytes`, `_detect_struct_indent`) and the empty-array `else` populate branch in `apply_mcl_set` likewise have no direct or branch coverage. | (a) Add a test that performs two distinct adds (or pre-seeds a higher-index entry) and asserts the second lands at CHANNEL_3 / PIN_3, proving the scan so a hardcoded id fails the gate (Reviewer verified at runtime: a second distinct add yields struct 3 / CHANNEL_3 / PIN_3). (b) Add a direct test for `_extract_channel_index` / `_extract_pin_index` on malformed input (returns None) and a test exercising the empty FlexioMclLogicChannels populate branch. (c) Reviewer checklist: when an acceptance value equals the fixtures trivial next value, require a test that perturbs the fixture so "computed" cannot be satisfied by a constant. |
| LL-010 | A module provider's `plan()` description and its declared ownership went stale after the apply path was corrected: the green gate stayed green while `basenxp.plan()` still told the user it would write `OsIfSystemTimerClockFreq=48000000` with "no core-clock ref in this project", even though `apply_basenxp_set` now writes a populated `OsIfSystemTimerClockRef` (Mcu `FLEXIO_CLK`/CORE_CLK) + an empty Freq array. The plan also never declared the cross-module Mcu read-dependency it now relies on. Separately, the fix to `apply.py`/`osif.json` was made by the **Tester**, whose charter is "edit tests only; report production gaps". | The convergence gate exercises `apply()` (and the vendor `.mex`) but nothing asserts `plan()`'s emitted `description`/`owner` or the declared dependency set, so plan and apply drifted with no failing test. The role deviation happened because a correct, fast production fix was reachable mid-gate and the boundary was not re-stated in the Tester handoff. | (a) Add a test that pins `BaseNxpProvider.plan()` output: its description must match what `apply` writes (populated ClockRef, empty Freq array, no `48000000`), and the plan must declare the Mcu `McuClockReferencePoint` dependency (owner/needs), so plan-vs-apply drift fails the gate. (b) Architecture rule: a cross-module READ that an edit depends on (here Mcu clock-ref discovery) must be an explicit declared dependency in `plan()`, not implicit in apply. (c) Process guard: when the Tester finds a production gap it reports it for the Worker; if the orchestrator authorizes an exceptional Tester-side production fix, a **fresh independent Tester** re-runs the gate (done here) AND the Reviewer treats any Tester-authored production diff as a required focus area. |
